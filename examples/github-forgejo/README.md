# Example: GitHub → Forgejo

This is the reference use case for Shotgun: exposing a **GitHub-shaped** API
that's actually backed by a self-hosted **Forgejo** (or Gitea) instance —
useful if you have tooling built against the GitHub REST API that you'd
rather point at your own forge without rewriting every client.

## Files here

- `github-api.json` — a small illustrative subset of the GitHub REST API
  (OpenAPI 3.0): `GET /repos/{owner}/{repo}`, `GET /user`, the pull-request
  merge endpoint, commit listing, and an Actions endpoint with no Forgejo
  equivalent. The real spec is much larger; download it from
  [github/rest-api-description](https://github.com/github/rest-api-description)
  and swap it in for full coverage.
- `forgejo-api.json` — the matching subset of the Forgejo API (Swagger 2.0).
  Grab the full spec from a running instance at `/api/swagger.json` or from
  [forgejo/forgejo](https://codeberg.org/forgejo/forgejo).
- `mappings.toml` — generated by `shotgun init` against the two files above,
  then hand-edited in the two spots the auto-diff couldn't resolve on its
  own (see the `edited = true` entries and their comments).

## Regenerating

```sh
cargo run -- init \
  --source examples/github-forgejo/github-api.json \
  --target examples/github-forgejo/forgejo-api.json \
  --output examples/github-forgejo/mappings.toml
```

Shotgun's matcher is deterministic: an endpoint auto-maps only when the
method + normalized path match exactly in both specs, or (failing that) the
`operationId` matches exactly. No fuzzy scoring, no path-similarity
percentages. Fields work the same way — only exact name+compatible-type
matches are auto-mapped; everything else is listed for a human to resolve.
That ran 3/5 endpoints through clean, and left two for a human:

- `GET /repos/{owner}/{repo}` — path+method match. `homepage`/`website` are
  the same field under different names, but the matcher won't guess that —
  it originally listed `homepage` as a default and `website` as a drop.
  Hand-edited into a proper rename (`edited = true`). Same story for
  `node_id`/`topics` (GitHub-only, defaulted) and `internal_tracker`
  (Forgejo-only, dropped) — those really are one-sided, so they're left as
  auto-generated.
- `GET /user` — path+method match. `name`↔`full_name` and
  `created_at`↔`created` needed the same hand-added-rename treatment, both
  at the endpoint level and in the shared `User` schema map.
- `GET /repos/{owner}/{repo}/commits` — path+method match; the
  `per_page`↔`limit` query param rename is hand-added the same way (query
  params aren't guessed either).
- `PUT .../pulls/{pull_number}/merge` — the normalized path matches
  Forgejo's `.../pulls/{index}/merge`, but the HTTP method doesn't (`PUT` vs
  `POST`), so auto-diff deliberately leaves it unmapped with a note rather
  than guessing. Confirmed and filled in by hand (`edited = true`),
  including the `pull_number`→`index` path param rename.
- `GET /repos/{owner}/{repo}/actions/runs` — no path or `operationId` match
  in the target spec at all (GitHub Actions isn't a Forgejo concept in this
  subset); left with an empty `target`, so it 501s until/unless you wire up
  something equivalent.

## Running it

```sh
shotgun serve \
  --mappings examples/github-forgejo/mappings.toml \
  --target-url https://forgejo.example.com \
  --listen 127.0.0.1:8080
```

Then point a GitHub-API-speaking client at `http://127.0.0.1:8080` instead
of `api.github.com`.
